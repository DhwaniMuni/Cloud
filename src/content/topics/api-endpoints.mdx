## What an endpoint actually is

Two programs need to talk. One is a web page running in someone's browser; the
other is a Java process running on a server. They do not share memory, they are
not in the same language, and they may not even be on the same continent. So they
agree on a set of **addresses** that one can ask about and the other will answer.

Each of those addresses is an **endpoint**.

An endpoint is made of two things, and it needs both:

| Part       | Example             | What it says             |
| ---------- | ------------------- | ------------------------ |
| **Method** | `GET`               | what kind of action      |
| **Path**   | `/api/resources/42` | what you want it done to |

That pairing matters more than it looks. `GET /api/resources/42` and
`DELETE /api/resources/42` point at the same resource but are two completely
separate pieces of code with opposite consequences. The path says _what_, the
method says _what to do with it_.

Here is the whole system for the read case — the browser, the backend, and the
database it pulls from:

The frontend has no idea DynamoDB exists. All it knows is that if it asks a

## Anatomy of a request

Underneath `fetch()` and Postman and every HTTP library, a request is just text
sent over a socket. Seeing it written out demystifies most of the vocabulary:

```text
POST /api/resources HTTP/1.1          ← method, path, protocol version
Host: localhost:8080                  ← which server
Content-Type: application/json        ← how to read the body below
Accept: application/json              ← what I would like back
                                      ← one blank line: headers end here
{                                     ← everything from here is the PAYLOAD
  "title": "AWS Well-Architected Framework",
  "url": "https://aws.amazon.com/architecture/well-architected/",
  "category": "cloud"
}
```

And the response has exactly the same shape — a status line, headers, a blank
line, then its own payload:

```text
HTTP/1.1 201 Created
Content-Type: application/json

{
  "resourceId": "7f3c9a12-8b4e-4c21-9d55-1a6f0e2b7c88",
  "title": "AWS Well-Architected Framework",
  "url": "https://aws.amazon.com/architecture/well-architected/",
  "category": "cloud"
}
```

### So what is a payload?

The **payload** is the body — the data itself, after the blank line. Everything
above the blank line is addressing and metadata; the payload is the cargo.

- A **`POST`** sends a payload: "here is the resource I want you to create."
- A **`GET`** normally sends no payload. Everything it needs fits in the URL,
  which is what makes a GET link-shareable and cacheable.
- A **`DELETE`** usually sends no payload either — the id in the path is enough.
- Almost every response carries a payload, except deliberately empty ones like
  `204 No Content`.

<Callout variant="note" title="Payload, body, JSON — the same thing, loosely">
  People use "payload", "request body" and "the JSON" interchangeably. Strictly, the body is the
  slot and JSON is one possible format for what goes in it — a file upload has a body too and it is
  not JSON. In practice, if someone says "check the payload", they mean look at the JSON.
</Callout>

```bash
# Only needed the first time, and whenever package.json changes.
npm install

# Dev server with hot reload. Also blocks; leave it open too.
npm run dev
```

Two things about this that were not obvious to me at the start:

- **Both commands block on purpose.** They are not scripts that finish — they are
  long-running servers. Two terminals is the normal state of things, not a
  workaround.
- **The two processes are strangers.** They only meet over HTTP. If the backend
  is not up, the frontend still loads perfectly and then fails on every request,
  which is a genuinely confusing first experience.

<Callout variant="warning" title="`mvn clean install` is not a one-time setup step">
  Any time the backend behaves like it is running code you already deleted, the answer is `mvn clean
  install`. Stale classes in `target/` produce errors that make no sense against the source in front
  of you.
</Callout>

Once a request arrives, it moves through three layers on its way to the data and

## GET: reading one resource

This is the endpoint I wrote first, and it is worth going through line by line:

```java
@GetMapping("/{resourceId}")
public ResponseEntity<Resource> getResource(@PathVariable String resourceId) {
    Resource resource = resourceService.getResource(resourceId);
    if (resource == null) {
        return ResponseEntity.notFound().build();
    }
    return ResponseEntity.ok(resource);
}
```

Reading it in order:

- **`@GetMapping("/{resourceId}")`** registers this method to answer `GET`
  requests. The path is relative to the controller's own `@RequestMapping`, so
  with `/api/resources` on the class, the full address is
  `/api/resources/{resourceId}`.
- **`{resourceId}`** in braces is a path variable — a slot, not a literal. A
  request to `/api/resources/42` matches, with `resourceId` bound to `"42"`.
- **`@PathVariable String resourceId`** is what pulls that slot out of the URL
  and hands it to your code as an ordinary Java string. The name has to match the
  name in the braces.
- **`ResponseEntity<Resource>`** is the return type because we want to control
  the status code _and_ the body. Returning plain `Resource` would always mean
  200, which is exactly the flexibility we need here.
- **`ResponseEntity.notFound().build()`** is a 404 with no body. `build()` is
  there because there is nothing to attach.
- **`ResponseEntity.ok(resource)`** is 200 plus the object, which Spring
  serialises to JSON automatically.

That `null` check is the entire lesson of the method. Without it a missing id
becomes a 500 and a stack trace; with it, "that does not exist" is a normal,
readable answer.

### The controller it lives in

```java
@RestController
@RequestMapping("/api/resources")
public class ResourceController {

    private final ResourceService resourceService;

    // Constructor injection: Spring supplies the service at startup, and the
    // field can be final. No @Autowired annotation needed.
    public ResourceController(ResourceService resourceService) {
        this.resourceService = resourceService;
    }

    @GetMapping
    public List<Resource> listResources() {
        // Returning a plain list is fine here — a collection read is always 200,
        // and an empty list is a valid answer, not a 404.
        return resourceService.listResources();
    }

    @GetMapping("/{resourceId}")
    public ResponseEntity<Resource> getResource(@PathVariable String resourceId) {
        Resource resource = resourceService.getResource(resourceId);
        if (resource == null) {
            return ResponseEntity.notFound().build();
        }
        return ResponseEntity.ok(resource);
    }
}
```

`@RestController` is the piece doing the invisible work: it tells Spring that
whatever these methods return is the response body, and to convert it to JSON
rather than look for an HTML template.

## Where the data actually comes from

The service and repository are what turn an id into a row. The repository is the
only class that imports anything AWS-shaped:

```java
@Repository
public class ResourceRepository {

    private final DynamoDbTable<Resource> table;

    public ResourceRepository(DynamoDbEnhancedClient enhancedClient) {
        this.table = enhancedClient.table("Resources", TableSchema.fromBean(Resource.class));
    }

    public Resource findById(String resourceId) {
        // DynamoDB looks items up by partition key. There is no "WHERE" here —
        // this is a direct key lookup, which is why it is fast and why the key
        // design matters so much.
        return table.getItem(Key.builder().partitionValue(resourceId).build());
    }

    public List<Resource> findAll() {
        // A scan reads the whole table. Fine for a small catalogue, and the
        // first thing to replace with a query or index once it grows.
        return table.scan().items().stream().toList();
    }

    public void save(Resource resource) {
        table.putItem(resource);
    }

    public void deleteById(String resourceId) {
        table.deleteItem(Key.builder().partitionValue(resourceId).build());
    }
}
```

The model class carries the mapping between Java fields and DynamoDB attributes:

```java
@DynamoDbBean
public class Resource {

    private String resourceId;
    private String title;
    private String url;
    private String category;

    // The partition key: the single attribute DynamoDB uses to find this item.
    @DynamoDbPartitionKey
    public String getResourceId() {
        return resourceId;
    }

    public void setResourceId(String resourceId) {
        this.resourceId = resourceId;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    // ... remaining getters and setters
}
```

<Callout variant="insight" title="The partition key is a design decision, not a detail">
  In DynamoDB you fetch by key. There is no ad-hoc `WHERE category = 'cloud'` that stays fast — you
  either scan the table or add an index you planned for. Choosing `resourceId` as the partition key
  decided, up front, which questions this table can answer cheaply.
</Callout>

## Displaying it in the frontend

With the endpoint returning JSON, the frontend's job is small: call it, handle
the three states it can be in, and render.

```tsx
import { useEffect, useState } from 'react';

interface Resource {
  resourceId: string;
  title: string;
  url: string;
  category: string;
}

export function ResourceList() {
  const [resources, setResources] = useState<Resource[]>([]);
  const [error, setError] = useState<string | null>(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    // A relative path, so the dev server proxies it to localhost:8080 and the
    // browser sees a same-origin request. No CORS involved.
    fetch('/api/resources')
      .then((response) => {
        // fetch() only rejects on network failure — a 404 or 500 still resolves,
        // so the status has to be checked by hand.
        if (!response.ok) {
          throw new Error(`Request failed with status ${response.status}`);
        }
        return response.json() as Promise<Resource[]>;
      })
      .then(setResources)
      .catch((cause) => setError(cause.message))
      .finally(() => setLoading(false));
  }, []);

  if (loading) return <p>Loading resources…</p>;
  if (error) return <p role="alert">Could not load resources: {error}</p>;
  if (resources.length === 0) return <p>No resources yet.</p>;

  return (
    <ul>
      {resources.map((resource) => (
        <li key={resource.resourceId}>
          <a href={resource.url}>{resource.title}</a> <span>{resource.category}</span>
        </li>
      ))}
    </ul>
  );
}
```

The `response.ok` check is the part that catches people out. `fetch()` treats a
404 as a request that _succeeded_ in reaching the server — the promise resolves
happily and you end up calling `.json()` on an error page. Checking the status is
not defensive programming; it is the required step.

An empty list and a failed request also have to render differently. "No resources
yet" and "the backend is down" look identical if you only track one state.

## POST: creating a resource

A POST is the first endpoint with a request payload, which means the first use of
`@RequestBody`:

```java
@PostMapping
public ResponseEntity<Resource> createResource(@Valid @RequestBody ResourceRequest request) {
    Resource created = resourceService.createResource(request);

    // 201 Created, with a Location header pointing at the new resource — so the
    // caller learns the generated id without having to guess the URL.
    URI location = URI.create("/api/resources/" + created.getResourceId());
    return ResponseEntity.created(location).body(created);
}
```

- **`@RequestBody`** is the mirror image of `@PathVariable`: it takes the JSON
  payload and deserialises it into a Java object. `@PathVariable` reads the
  address, `@RequestBody` reads the cargo.
- **`ResourceRequest`** is deliberately not `Resource`. The client should not get
  to set the id, so the incoming shape only contains the fields it is allowed to
  supply.
- **`@Valid`** makes Spring check the annotations on that class before your
  method runs, so a missing `title` is a 400 you never wrote code for.
- **`ResponseEntity.created(...)`** returns 201 rather than 200. 200 means "here
  is your answer"; 201 means "I made something new, and here is where it lives".

```java
public class ResourceRequest {

    @NotBlank(message = "title is required")
    private String title;

    @NotBlank(message = "url is required")
    private String url;

    private String category;

    // getters and setters
}
```

## DELETE: removing a resource

```java
@DeleteMapping("/{resourceId}")
public ResponseEntity<Void> deleteResource(@PathVariable String resourceId) {
    // DynamoDB's delete is idempotent: deleting a key that was never there is a
    // success. Reading first is what lets us honestly answer 404.
    if (resourceService.getResource(resourceId) == null) {
        return ResponseEntity.notFound().build();
    }

    resourceService.deleteResource(resourceId);

    // 204 No Content: it worked, and there is deliberately nothing to send back.
    return ResponseEntity.noContent().build();
}
```

`ResponseEntity<Void>` is the type for "a status code and no body". The read
before the delete is not paranoia — without it every DELETE returns success,
including for ids that never existed, and you lose the only signal that would
have told you the key was wrong.

## Verifying it in Postman

Postman fires HTTP requests directly at the backend, with no browser and no
frontend in the way. That is its real value: when a request fails there, the
frontend is not the problem, and when it succeeds there but fails in the app, the
frontend definitely is.

Deleting a resource end to end — the sequence I ran for every endpoint:

1. **Confirm it exists.** `GET http://localhost:8080/api/resources` and copy a
   real `resourceId` out of the response. Never invent an id for a test.
2. **Set up the delete.** New request, method **DELETE**, URL
   `http://localhost:8080/api/resources/<the id you copied>`. No body needed —
   the id is in the path.
3. **Send it.** Expect **204 No Content** and an empty response pane. An empty
   body here is the correct answer, not a sign nothing happened.
4. **Confirm it is gone.** `GET http://localhost:8080/api/resources/<same id>`
   should now return **404 Not Found**.
5. **Confirm the collection agrees.** `GET /api/resources` should come back one
   item shorter.

Step 4 is the one that actually proves anything. A 204 on its own only says the
server did not throw.

For the POST, the setup is slightly different because there is a payload:

```text
POST http://localhost:8080/api/resources
Body → raw → JSON

{
  "title": "AWS Well-Architected Framework",
  "url": "https://aws.amazon.com/architecture/well-architected/",
  "category": "cloud"
}
```

Choosing **JSON** in that dropdown is what sets `Content-Type: application/json`.
Leave it on **Text** and the request is rejected with a 400 before it reaches any
code you wrote — which looks like a bug in the endpoint and is not.

<Callout variant="insight" title="Postman never sees a CORS error">
  CORS is enforced by browsers, not servers. So an endpoint that works perfectly in Postman and
  fails in the browser is almost never broken — it is a cross-origin problem. Knowing which of the
  two tools *can* produce a given error narrows things down before you read a single log line.
</Callout>

## Putting it together

The four endpoints, and what each one taught:

| Endpoint                     | Payload in | Success | Idea                              |
| ---------------------------- | ---------- | ------- | --------------------------------- |
| `GET /api/resources`         | none       | `200`   | a collection read; empty is valid |
| `GET /api/resources/{id}`    | none       | `200`   | path variables, and honest `404`s |
| `POST /api/resources`        | JSON       | `201`   | request bodies and validation     |
| `DELETE /api/resources/{id}` | none       | `204`   | status codes with no body         |

None of these are complicated on their own. What took the time was learning that
the address, the method, the headers, the payload and the status code are five
separate things — and that most confusing failures are one of them being wrong
while the other four look fine.
