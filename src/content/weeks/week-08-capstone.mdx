The capstone began as ordinary RAG: embed the docs, retrieve the top _k_ chunks,
stuff them into a prompt, return the answer. It worked, and it was also a
dead end — it could answer questions but could not *do* anything, and the
orchestration logic lived in my application where every new capability meant
another branch.

## Where it started: Retrieve + Converse

The original flow put my service in the middle of every decision:

```java
// The orchestration I ended up deleting.
RetrieveRequest retrieve = RetrieveRequest.builder()
    .knowledgeBaseId(knowledgeBaseId)
    .retrievalQuery(q -> q.text(userQuestion))
    .retrievalConfiguration(c -> c.vectorSearchConfiguration(v -> v.numberOfResults(5)))
    .build();

List<KnowledgeBaseRetrievalResult> chunks =
    bedrockAgentRuntime.retrieve(retrieve).retrievalResults();

// I decide the prompt shape, the citation format, and whether to retrieve at all.
String context = chunks.stream()
    .map(r -> r.content().text())
    .collect(Collectors.joining("\n\n---\n\n"));

ConverseRequest converse = ConverseRequest.builder()
    .modelId(modelId)
    .system(s -> s.text(SYSTEM_PROMPT.formatted(context)))
    .messages(m -> m.role(ConversationRole.USER).content(c -> c.text(userQuestion)))
    .build();
```

Every question took exactly one retrieval, whether or not it needed one, and
"check whether ticket ABC-123 is still open" was unanswerable — there was no
path from the model to an API call.

## Where it ended: one InvokeAgent call

The replacement is close to embarrassingly small:

```java
InvokeAgentRequest request = InvokeAgentRequest.builder()
    .agentId(agentId)
    .agentAliasId(agentAliasId)
    .sessionId(sessionId)        // conversation memory is the agent's problem now
    .inputText(userQuestion)
    .enableTrace(true)           // the only way to see what it decided to do
    .build();

// The response is an event stream: text chunks, citations, and trace events
// interleaved. Progress states come from the trace, not from guesswork.
bedrockAgentRuntime.invokeAgent(request, InvokeAgentResponseHandler.builder()
    .subscriber(visitor -> visitor
        .onChunk(chunk -> emitter.text(chunk.bytes().asUtf8String()))
        .onTrace(trace -> emitter.progress(describe(trace)))
        .build())
    .build());
```

<Callout variant="insight" title="What actually changed">
  The line count barely moved — but the *decisions* moved. Whether to retrieve, how
  many times, whether to call a tool first: those were `if` statements in my service
  and are now the agent's job. My service is a transport layer again.
</Callout>

### Reading traces instead of reading logs

Enabling `enableTrace` was not optional. Without it, a wrong answer is a black
box. With it, you can see the rationale, the retrieval queries the agent actually
issued (often a rewritten version of the user's question), and which action group
it chose. Most of my debugging this week was reading traces, not stack traces.

## The Lambda-backed action group

An action group is how the agent reaches outside its own knowledge. The contract
is an OpenAPI schema the agent reads to decide *whether* and *how* to call you:

```json
{
  "openapi": "3.0.0",
  "paths": {
    "/tickets/{ticketId}": {
      "get": {
        "operationId": "getTicketStatus",
        "description": "Return the current status, assignee, and last update time for one ticket. Use when the user asks whether work is done, who owns it, or when it last moved.",
        "parameters": [
          {
            "name": "ticketId",
            "in": "path",
            "required": true,
            "schema": { "type": "string", "pattern": "^[A-Z]{2,10}-[0-9]{1,6}$" }
          }
        ]
      }
    }
  }
}
```

The `description` is not documentation — it is the prompt the agent uses to route.
Vague descriptions produced an agent that called the tool for everything or never
called it at all; being explicit about *when* to use it fixed the routing.

<Callout variant="warning" title="The model supplies the arguments">
  An action group is a public endpoint whose caller is a language model. Validate
  everything: I match `ticketId` against the pattern above inside the Lambda too,
  because a schema in the OpenAPI document is a hint to the model, not a guarantee
  at the boundary.
</Callout>

## Citations that a human can follow

The Knowledge Base returns chunk-level references. To turn those into something
clickable, I attach metadata at ingestion time using sidecar files:

```json
{
  "metadataAttributes": {
    "title": "Deploying the payments service",
    "sourceUrl": "https://wiki.internal/eng/payments/deploy",
    "section": "rollback",
    "status": "current",
    "updatedAt": "2026-07-14"
  }
}
```

That `status` attribute is what powers the retrieval filter that fixed the
deprecated-runbook problem — the answer to "stop citing the old doc" was to stop
retrieving it:

```java
RetrievalFilter currentOnly = RetrievalFilter.builder()
    .equals(f -> f.key("status").value(Document.fromString("current")))
    .build();
```

Each returned chunk carries these attributes back, so the API maps them into a
citation list — title, section, and a real URL — that the React client renders
beneath the answer. Users click through and verify. That single affordance did
more for trust than any change to the prompt.

### What I would do next

- **Evaluate systematically.** I tested by asking questions I already knew the
  answers to, which is not evaluation. A fixed question set with expected sources
  would have caught the deprecated-doc problem on day one instead of day three.
- **Guardrails on the action group.** Read-only tools are forgiving. The moment one
  can write, "the model chose the arguments" stops being a footnote.
- **Cache retrieval for repeated questions.** A meaningful fraction of queries were
  near-duplicates, and every one paid full embedding and search cost.
