The week started with a service that ran on my laptop and a deploy process that was
three paragraphs of instructions in a Slack thread. It ended with a push to `main`
producing a running container in ECS without anyone touching the console.

## The pipeline, end to end

Four stages, each one an artifact handoff rather than a shared filesystem:

<PipelineDiagram
  caption="Commit to production: every stage hands the next one an immutable artifact."
  stages={[
    { label: 'Source', detail: 'Push to main; CodePipeline picks up the commit', icon: '◇' },
    { label: 'Build', detail: 'CodeBuild runs tests, builds the image, tags it with the commit SHA', icon: '▢' },
    { label: 'Push', detail: 'Image goes to ECR; the SHA tag is the only identifier downstream', icon: '△' },
    { label: 'Deploy', detail: 'New ECS task definition revision, rolling update behind the ALB', icon: '○' },
  ]}
/>

The important property is that **nothing after the build stage knows about my
source code**. The build produces an image digest; every later stage refers to
that digest. That is what makes a rollback trivial — you re-deploy an older
digest rather than rebuilding an older commit.

<Callout variant="insight" title="Tag with the commit SHA, not `latest`">
  `latest` is a mutable pointer, which means two deploys of "the same" tag can ship
  different code. Tagging with the immutable commit SHA made every deploy traceable
  back to one line of `git log`, and made "which version is actually running?" a
  question with an answer.
</Callout>

## Containerising the service

The first Dockerfile I wrote was a single stage that shipped the whole JDK and a
Maven cache — around 700 MB. A multi-stage build cut it to roughly 180 MB, and
more importantly stopped shipping build tooling into production:

```dockerfile
# ---- build stage ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /build

# Copy the POM first so dependency resolution is cached independently of source
# changes — this layer only invalidates when dependencies actually change.
COPY pom.xml .
RUN mvn -B dependency:go-offline

COPY src ./src
RUN mvn -B clean package -DskipTests=false

# ---- runtime stage ----
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# Never run as root: a container escape should not land on a privileged user.
RUN addgroup -S app && adduser -S -G app app
USER app

COPY --from=build --chown=app:app /build/target/*.jar app.jar

EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]
```

Two details that mattered more than I expected:

- **Copy `pom.xml` before `src`.** Docker caches per layer, so putting dependency
  resolution above the source copy means a code change does not re-download the
  world. This took CI builds from ~4 minutes to ~50 seconds on a warm cache.
- **`MaxRAMPercentage`, not `-Xmx`.** The JVM reads the container's memory limit,
  so a percentage adapts when the task definition changes. A hardcoded `-Xmx`
  silently becomes wrong the moment someone resizes the task.

### The task definition as a build artifact

The task definition is where the image, the resource limits, and the log
configuration meet. I kept it in the repo with a placeholder for the image, and
had CI substitute the real digest:

```json
{
  "family": "ignite-api",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "512",
  "memory": "1024",
  "executionRoleArn": "arn:aws:iam::ACCOUNT_ID:role/ecsTaskExecutionRole",
  "taskRoleArn": "arn:aws:iam::ACCOUNT_ID:role/igniteApiTaskRole",
  "containerDefinitions": [
    {
      "name": "api",
      "image": "ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/ignite-api:IMAGE_TAG",
      "portMappings": [{ "containerPort": 8080, "protocol": "tcp" }],
      "essential": true,
      "environment": [{ "name": "SPRING_PROFILES_ACTIVE", "value": "prod" }],
      "secrets": [
        {
          "name": "DB_PASSWORD",
          "valueFrom": "arn:aws:secretsmanager:us-east-1:ACCOUNT_ID:secret:ignite/db-password"
        }
      ],
      "healthCheck": {
        "command": ["CMD-SHELL", "wget -q --spider http://localhost:8080/actuator/health || exit 1"],
        "interval": 30,
        "timeout": 5,
        "retries": 3,
        "startPeriod": 90
      },
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/ignite-api",
          "awslogs-region": "us-east-1",
          "awslogs-stream-prefix": "ecs"
        }
      }
    }
  ]
}
```

<Callout variant="warning" title="Two roles, two jobs">
  `executionRoleArn` is what the ECS agent uses to pull the image and write logs.
  `taskRoleArn` is what *your application code* uses to call AWS. Conflating them
  is how a web service ends up with permission to pull images — and how a
  "permission denied" ends up in the wrong place entirely.
</Callout>

## Fronting S3 with CloudFront

The frontend is a static bundle, so it does not need a server — but it does need
HTTPS, a custom domain, and edge caching. The pattern I settled on keeps the
bucket **completely private**:

- Bucket blocks all public access; no bucket policy grants `*`.
- CloudFront uses an **Origin Access Control (OAC)**, and the bucket policy trusts
  only that distribution's ARN.
- A default root object of `index.html`, plus a 403/404 → `/index.html` (200)
  response mapping so client-side routes deep-link correctly.

The deploy is two syncs with different cache semantics, then a narrow invalidation:

```bash
# Hashed assets are immutable — cache them aggressively and never invalidate.
aws s3 sync ./dist s3://"$BUCKET" \
  --delete \
  --exclude index.html \
  --cache-control "public, max-age=31536000, immutable"

# The entry point must always be revalidated, or users get an HTML file
# pointing at bundles that no longer exist.
aws s3 cp ./dist/index.html s3://"$BUCKET"/index.html \
  --cache-control "no-cache, must-revalidate"

# Invalidate only what can actually be stale. `/*` would work but costs more
# and hides the fact that everything else is content-addressed.
aws cloudfront create-invalidation \
  --distribution-id "$DISTRIBUTION_ID" \
  --paths /index.html
```

## GitHub Actions as the front door

CodePipeline handles the AWS-side orchestration, but PR validation lives in GitHub
Actions, and it authenticates with **OIDC rather than long-lived access keys**:

```yaml
permissions:
  id-token: write # required to request the OIDC token
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5

      - uses: aws-actions/configure-aws-credentials@v5
        with:
          role-to-assume: arn:aws:iam::ACCOUNT_ID:role/github-actions-ignite
          aws-region: us-east-1

      - name: Build image (no push on PRs)
        run: docker build -t ignite-api:${{ github.sha }} .
```

Deleting the last static access key from the repo secrets was the most satisfying
part of the week. There is nothing left to leak.
